# LexiVault 项目说明与实施规范

> 版本：1.0 · 编写日期：2026-10-15 · 草稿恢复：2026-10-16  
> 需求依据：本次对话中新描述的科研场景。本文件重新定义产品，不沿用此前项目文档。  
> 阅读方式：前半部分描述完整产品目标，后半部分区分本轮可试用功能与后续工程任务。文中的“建议”“目标”“拟采用”均不代表已经实现或测试通过。最终实施与验证状态以交付 README 为准。

## 1. 产品定位

LexiVault 是一个以个人文献库为基础的科研工作空间，帮助刚进入研究领域的研究生把“找到文献、读懂文献、记录理解、安排研究、建立主题联系、提出可验证的问题”连成一条连续的工作流程。

产品的核心对象是用户自己积累的文献、阅读笔记、研究计划及其联系。科研智能体是这些资料之上的研究助手：先检索用户授权的资料，再给出能回到原文的分析。它应当帮助用户减少重复寻找资料、整理证据和切换软件的成本。能否提升选题质量，需要用真实任务验证，不能先假定优于所有通用大模型。

一句话描述：**把自己的文献读成可追溯的知识，再把知识组织成下一步可执行的研究。**

### 1.1 主要用户

| 用户 | 当前困难 | 产品应提供的帮助 |
| --- | --- | --- |
| 研一学生、刚转方向的研究者 | 不知道先读什么、文章之间有什么联系 | 主题检索、阅读清单、关键词图谱、可解释的阅读建议 |
| 正在进行课题的研究生 | 文献、灵感和实验安排分散在不同文件里 | 原文旁记笔记、带日期的研究计划、笔记双向链接 |
| 积累了一定资料的研究者 | 很难整体比较方法、结论与不足 | 有证据的跨文献比较、近期进展梳理、选题与实验方案草案 |

首个正式版本服务单人科研，不把多人实时协作、课题组权限和导师审批加入第一阶段。

### 1.2 设计原则

- 以阅读和研究行为为主，不做以数字卡片为主体的数据看板。
- 六个一级入口各自承担一项明确职责；同一能力不再以“资料库、知识库、文献库”等近义名称重复出现。
- 日间采用暖象牙、梅紫、浅黄铜与雾灰；夜间采用暖炭、低饱和梅紫与柔金。保留已有品牌和登录注册页面。
- 文献、笔记与计划有稳定标识，能够互相跳转；页面之间使用同一份对象，而不是复制出互不一致的内容。
- 自动处理必须能看到来源、阶段和失败原因。示例数据、解析结果、模型推断与人工确认要有明确区别。
- 原始文件属于用户，编辑后的内容是新的可保存对象；任何导入转换都保留原件，不承诺对任意格式进行无损往返编辑。

## 2. 完整科研场景

以“刚进入分子图学习方向的研一学生”为例：

1. 用户在“文献发现”中输入研究主题，选择近几年、论文类型和开放获取条件，查看检索结果及来源。
2. 用户把选定条目加入自己的知识库。平台先保存元数据，再获取允许下载的原文；没有全文时仍保存条目，并显示“仅元数据”。
3. 获取与解析任务在“知识库管理”中显示进度。用户可补充本地 PDF、修正摘要和合并重复条目。
4. 用户进入“文献阅读”。左侧按目录展开文献，中间阅读原文，右侧记录方法、疑问和灵感。引用原文时保存页码、段落和文献标识。
5. 用户把一个问题记为 `[[小样本分子性质预测]]`，并在“研究计划”中新建本周阅读安排，关联相关文献和笔记。
6. 用户导入本地 Word 计划，检查转换结果，继续编辑段落、字体、颜色、高亮和待办，并保留原 Word 文件作为附件。
7. 用户在“主题图谱”中选定“图神经网络”和“分子性质预测”，将多个本地库纳入范围，查看哪些文献的摘要包含这些主题，点开节点即可定位到文献。
8. 随着文献增多，后台增量解析并更新检索索引。用户可以查看哪部分已可检索，哪部分只有摘要，哪部分解析失败。
9. 用户向“科研智能体”提出“结合我库中近三年的工作，有哪些值得验证的小样本研究方向”。智能体明确资料范围和时间窗口，检索证据，再给出候选方向、支持证据、反例、缺口与不确定性。
10. 用户选定一个候选方向，将其保存为研究计划，补充基线、数据集、消融和成功标准，再开始实际研究。

文献数量不是解锁功能的硬门槛：少量文献也能阅读、做计划或建局部图谱。资料少时，系统说明覆盖不足；资料多时，系统逐步聚合和过滤。

## 3. 工作空间信息架构

一级导航固定为以下六项，顺序贴合日常研究过程，同时保留科研智能体为默认首页。

| 唯一一级入口 | 核心问题 | 内容和主要操作 | 不承担的职责 |
| --- | --- | --- | --- |
| 科研智能体 | 基于我的资料，能得出什么有证据的分析？ | 对话、资料范围、引用、方法比较、选题和实验方案草案 | 不独立维护另一份文献库；不假装已经训练出私人基础模型 |
| 文献发现 | 去哪里寻找和获取新文献？ | 联合检索、筛选、DOI 导入、开放原文定位、加入库 | 不在这里编辑阅读笔记或管理后台索引任务 |
| 文献阅读 | 我正在读什么，理解和疑问是什么？ | 目录树、原文阅读器、原文定位、随文笔记、阅读状态 | 不再同时展示占宽的工作空间文字导航 |
| 研究计划 | 下一步做什么，为什么做，何时做？ | 富文本计划、任务、日期、附件、双向链接、计划关系图 | 不复制出独立的“任务中心”“笔记中心”和“日程中心” |
| 主题图谱 | 哪些文献围绕同一主题，接下来该读什么？ | 摘要关键词选择、跨库图谱、匹配依据、相关文献清单 | 不与研究计划的手工链接图混用边的含义 |
| 知识库管理 | 我的资料放在哪里、处理到哪一步？ | 库和来源、目录映射、导入、解析、索引、去重、重建和删除 | 不再作为第二个日常阅读页面 |

### 3.1 统一术语

| 术语 | 本项目中的精确定义 |
| --- | --- |
| 工作空间 Workspace | 用户当前的研究环境，包含多个知识库、计划和对话 |
| 知识库 Vault | 一个明确的资料集合及其元数据和索引范围，可映射一个本地根目录 |
| 文献 Paper | 一项学术作品，不等同于单个 PDF 文件；可有预印本、接受稿、正式版本等多个文件 |
| 文件 SourceFile | 原始二进制文件及其哈希、来源和版本 |
| 阅读笔记 ReadingNote | 与一篇文献或原文位置关联的用户记录 |
| 计划 Plan | 有正文、日期、状态及关联资料的研究安排文档 |
| 任务 Task | 计划中的可完成事项，可有截止日期；并非每一段笔记都是任务 |
| 关键词 Keyword | 从摘要识别或由用户确认的主题词，有规范名称、别名和来源 |
| 知识库就绪 | 指当前版本资料已完成选定的解析与索引，并非“AI 已完全理解所有论文” |

### 3.2 唯一入口与上下文操作

“唯一入口”指每个模块只有一个主导航入口，不在侧栏和顶部再各放一套同义菜单。上下文动作可以出现在资料旁，例如“加入研究计划”“在阅读器打开引用”，它们直接携带对象跳转到所属模块，不生成另一套编辑功能。

设置、主题切换、帮助和账号放在全局底部或顶部；它们是环境控制，不算科研功能模块。对话历史只属于科研智能体。进入阅读时，宽侧栏被文献目录树替代，保留窄图标轨道用于切换六个模块。

## 4. 六个页面的界面规范

### 4.1 科研智能体

采用阅读感强的对话布局。左侧为六项导航与当前对话历史；中间是对话和证据内容；资料选择在输入区附近。回答不堆满大面积数据卡片。

- 顶部展示当前工作空间、资料范围和模型连接状态。
- 输入前可选择整个工作空间、若干库或若干文献，并显示“截至何时建立的索引”。
- 输入区支持附加资料、停止请求和恢复草稿；未连接模型时如实说明。
- 回答按“结论、证据、局限、下一步”组织；引用可回到文献与页码。
- 方法比较表、实验变量表只在问题需要时出现，不作为固定首页看板。
- 选题建议可以保存到研究计划，附带生成时使用的证据和版本信息。

空状态给出“比较两篇论文的方法”“整理近三年的主题变化”等示例问题。示例问题是可点击输入，不伪造已发生的研究结论。

### 4.2 文献发现

采用“筛选与下载设置—结果列表—获取队列”的布局，延续已确认的文献发现设计。结果可展开摘要；知识库归属在确认获取之后选择。

- 顶部搜索研究主题或题名，来源支持 Semantic Scholar、Crossref、arXiv、OpenAlex、PubMed / PMC。未来可扩展作者、DOI 与更多适配器；当前搜索仅筛选明确标注的本地示例。
- 来源配置按官方接口区分匿名、Key、邮箱或订阅 Token；OpenAlex 游标批量获取要求已激活 Key。公开接口不虚构账号密码必填项。官方依据与条件字段见 [DISCOVERY-SOURCES.md](DISCOVERY-SOURCES.md)。
- 左侧原“入库位置”改为“配置下载路径”，定义爬取执行程序保存原始文件的路径、子目录与命名方式。浏览器前端仅保存配置，不直接写入任意磁盘目录。
- 结果展示题名、年份、资料类型、开放获取状态和摘要；生产接入后补充真实作者、DOI、版本与许可，未知字段保持未知。本地样例不伪造这些字段。
- 点结果加号加入获取队列，再点“确认获取到知识库”，选择目标知识库和目录，最后保存获取方案。下载路径与知识库逻辑位置分别配置。
- 当前仅在本地保存／导出方案，不实际爬取、下载、创建知识库或写入论文记录；API Key、Token 与邮箱不持久保存或导出。
- 未来执行阶段反馈排队、正在获取、成功、仅保存元数据或失败，不把元数据等同于已取得全文。

### 4.3 文献阅读：三列固定语义

桌面界面按用户要求采用竖向三列：**目录树／文献列表、文献原文、阅读笔记**。左侧宽导航转换成知识库与目录树，最左侧可保留窄图标轨道。

| 区域 | 建议默认宽度 | 内容 |
| --- | --- | --- |
| 全局窄图标轨道 | 约 60 px | 模块切换、主题和设置 |
| 左列 | 约 240–280 px | 库选择、逐层文件夹树、文献筛选、当前文献 |
| 中列 | 剩余空间的约 60% | 文献标签、页码与缩放、原文、选区引用 |
| 右列 | 约 320–400 px | 当前文献笔记、原文摘录、个人理解、问题与链接 |

列宽允许拖动并记忆。缩小窗口时优先保证原文可读：平板把目录或笔记变成可切换侧板；手机采用目录、原文、笔记三个页签，避免三列硬挤在同一屏。

阅读能力目标：PDF 页码与缩放、目录、全文搜索、定位引用；文本类文献使用语义化正文视图。选区添加笔记时保存文献 ID、文件版本、页码、选中文字和定位信息。文件版本变化后定位失效，要显示“原文版本已改变”，不能无声跳到错误段落。

右侧记录的“原文引用”和“我的理解”在视觉与数据上分开；用户想法不自动成为论文作者结论。笔记可链接到计划或主题，但不强制用户为每条记录创建额外卡片。

阅读笔记与研究计划是两个明确的文档上下文：阅读笔记围绕一篇文献及原文位置积累理解；研究计划围绕目标、时间和行动组织研究。两者可以互相链接，也可以把一条阅读灵感显式转为计划任务，但不把所有阅读笔记自动塞进任务文档。共享编辑器能力不代表合并它们的用途或数据归属。

### 4.4 研究计划

采用“计划目录／清单—正文编辑器—关联与安排”的布局。正文占据主要面积，接近文档编辑体验。左侧是当前模块自己的计划列表，主导航仍只保留一套。

- 顶部：计划标题、保存状态、新建、导入、导出。
- 正文：富文本工具栏和可编辑文档；支持段落、标题、加粗、斜体、下划线、字号、字体、文字颜色、高亮、列表、待办、引用、超链接与内部链接。
- 安排区：计划状态、开始／截止日期、标签或主题、任务清单、附件、出链和反向链接。
- 模块内部视图：文档、任务安排、关系图。它们共享同一组计划与任务，不成为新的一级功能。
- 日期只展示用户明确填写的日期，不臆测进度；未安排事项保留在未排期清单。
- 右侧关联区可收起，便于长文编辑。日间正文为暖白纸面，夜间保留舒适对比和原有强调色。

**本轮试用优先实现此模块的真实保存、编辑、导入、附件、双向链接、关系图、任务与备份流程。**

### 4.5 主题图谱

采用宽幅图谱画布。左上角为关键词与库范围；选中节点后的右侧信息抽屉提供摘要命中和文献列表。图谱默认围绕一至数个已选关键词展开。

- 关键词节点较大、标签清晰；文献节点较小，颜色表示库或主题群组，不能同时混用多种不可解释的颜色规则。
- 单个关键词居中；多个关键词形成几个稳定中心，共同命中的文献自然位于中心之间。
- 悬停突出一跳邻域，其余节点和边减弱；点击锁定选中，详情说明为什么发生连接。
- 缩放远时仅显示关键词和聚合群组；靠近时逐步显示文献名称与连线细节。
- 提供关键词联合／交集、年份、知识库、摘要可用状态和已读状态筛选。
- 点击文献可以进入阅读器；用户也可把筛选结果保存为阅读清单，保持筛选条件和生成时间。
- 关系统计只用于解释当前结果，不将首页改成图表仪表盘。

### 4.6 知识库管理

采用来源列表与处理详情布局，帮助用户了解“哪些资料参与了检索，以及为什么有资料尚不可用”。

- 左侧：多个知识库、来源类型、本地根目录或导入包。
- 主区：文件条目、作品关联、摘要是否存在、解析和索引状态、最近处理时间。
- 详情：原件、来源、许可证、版本、摘要修订、关键词确认、任务日志和错误原因。
- 操作：导入、关联目录、重新解析、重建索引、去重合并、移出库、删除原件。
- “移出库”和“删除磁盘文件”是不同动作；后者需要明确且具体的确认。
- 解析进度可使用任务列表与细进度条，不需要数据看板。

## 5. 研究计划功能的行为定义

### 5.1 计划与任务的关系

计划是有上下文的研究文档，例如“十月阅读与复现实验”。任务是其中可安排的事项，例如“复现一个基线并记录随机种子”。计划正文、任务清单和关系图引用同一计划 ID。

完整产品的计划状态建议为“待开始、进行中、已完成、已归档”；任务状态可以扩展为“待办、进行中、已完成”。状态与日期独立：到期不自动等于失败，完成也不自动删除正文。

后续独立任务可保存标题、备注、开始日、截止日、关联计划与排序。日期型任务按用户当地日历日处理，不因 UTC 转换前后漂移一天；精确时间戳另存时区和偏移。

**本轮试用的日期属于整份计划，正文待办只有勾选状态与完成进度，尚无每条待办的独立排期。** 计划安排视图支持按计划日期和状态查看，未排期计划单独列出。第一阶段不实现后台通知、日历账号同步或跨设备提醒，不能把页面中的日期等同于系统已经设置闹钟。

### 5.2 编辑与保存

- 工具栏作用于当前选区，操作后保留编辑焦点和撤销历史；不能以按钮点击导致丢失选区。
- 输入后自动保存，状态区区分“正在保存、已保存、保存失败”。未保存内容在当前内存仍保留，并提供导出路径。
- 标题为空时可使用“未命名计划”，文档 ID 不依赖标题。
- 计划列表可搜索标题和正文，支持新建、重命名、归档或删除。删除应防止误触；附件及反向引用的处理要明确。
- 粘贴和导入的 HTML 必须清洗；保留常见文档结构和允许的格式，移除脚本与外部自动加载资源。
- 不承诺完整 Word 排版引擎：页眉页脚、复杂分页、批注修订、公式对象、浮动图片和嵌套表格可能需要转为简化内容或保留在原件中。

### 5.3 双向链接

借鉴 Obsidian 的内部链接和反向链接思路，而不是复制其全部行为。Obsidian 官方文档区分 `[[笔记]]` 形式的内部链接，以及从被引用笔记回到引用者的反向链接；图谱表达笔记间连接。[内部链接](https://obsidian.md/help/links) · [反向链接](https://obsidian.md/help/plugins/backlinks) · [图谱](https://obsidian.md/help/plugins/graph)。

LexiVault 的计划链接规则：

1. 用户可在正文输入 `[[计划名称]]`，或使用“插入内部链接”选择已有计划。
2. 已解析链接绑定稳定的目标 ID；显示标题可随目标重命名更新。
3. 尚不存在的目标显示为“未创建”，点击时再由用户选择创建，不在后台无提示生成大量文档。
4. 同名计划需要选择目标，不能任意指向其中一个；别名和路径可作为消歧手段。
5. 右侧分别列出当前文档的出链和谁引用了它，并显示上下文片段。
6. 反向链接从正向链接计算，不能让用户另维护一份容易不一致的数据。
7. 删除目标后，保留正文中的引用及“目标在回收站”状态，避免悄悄丢失研究线索。

第一阶段重点支持计划与计划之间的关系。后续扩展到阅读笔记、文献、主题时，内部对象统一使用 `entityType + entityId`；不要把 DOI、标题和文件路径混成同一个 ID。

### 5.4 计划关系图与近期关注

计划关系图中的节点是计划文档，边表示用户明确建立的内部链接。它与“主题图谱”使用不同的边和图例：前者表达用户组织研究的意图，后者表达摘要中可核对的主题匹配。

关系图可按日期、计划状态、关键词筛选，点击节点打开文档，悬停显示一跳关系。近期关注可以依据“近期修改、任务完成记录、显式标签和链接数量”辅助观察，但应将指标命名为“近期编辑／关联”，不能据此断言真实投入时间或研究成果。用户没有计时时，系统不知道实际花了多少小时。本轮先提供标题／标签查找及近两周编辑标签关联，完整筛选能力随正式版完善。

## 6. 文档导入与附件规范

用户的“任何形式文档传入”按两个层次实现：**所有允许大小的文件都可作为原始附件保存；能解析的常见格式再转换为可编辑内容**。传入、预览、正文转换、格式保真是四件不同的事。

| 格式 | 本轮计划处理方式 | 明确的保真边界 |
| --- | --- | --- |
| DOCX | 解析包内文档结构，导入段落、常见文字样式、列表和表格内容；保留原件 | 复杂版面、修订、公式和浮动对象不承诺一致 |
| ODT | 解析文本结构及可识别样式，生成可编辑正文；保留原件 | 页面布局与特殊对象可能简化 |
| RTF | 提取常见段落及格式为可编辑内容；保留原件 | 字符编码、复杂表格、嵌入对象存在差异 |
| Markdown / TXT | 转为可编辑段落；识别支持的 Markdown 结构 | Markdown 方言和 HTML 扩展按支持范围处理 |
| HTML / HTM | 清洗后导入支持的标签和格式 | 脚本、事件、iframe、外部资源与任意 CSS 不执行 |
| CSV | 解析带引号和转义的表格内容，转换为可编辑表格 | 不把 CSV 公式作为可执行表达式 |
| JSON | 普通 JSON 作为格式化结构文本导入；完整恢复使用自有 ZIP | 任意 JSON 不自动猜测成可执行任务或运行脚本 |
| 有文本层的 PDF | 尝试提取文字，形成可编辑草稿，保留原 PDF | 阅读顺序、公式与表格可能丢失；不承诺还原版面 |
| 扫描 PDF | 保留原件；无 OCR 服务时明确说明无法得到正文 | 不伪造已完成 OCR |
| 旧版二进制 DOC | 原始附件保存并可下载 | 不以改扩展名或文本解码假装已转换为可编辑 Word |
| 图片、压缩包、演示稿及其他二进制格式 | 按附件保存并显示格式；支持时可预览 | 没有解析器时不声称可编辑其内部内容 |

上表是本轮目标范围，实际可编辑支持以交付版本的“导入说明”和格式样例测试为准；尚未验证的格式不能写成已经验证支持。所有转换在用户选择文件后进行；首轮试用默认在浏览器内处理。导入完成给出转换摘要，例如“正文已导入，原件已保留；复杂对象请查看原件”。某一文件失败不应阻止同批其他文件保存。

正文导出提供 Word DOCX、Markdown 和 HTML。DOCX／HTML 尽量保留受支持的文字样式与结构；Markdown 表达其语法允许的内容，文字颜色、字号、高亮等富文本属性不保证完整保留。DOCX 本轮用占位说明表示正文图片，HTML 可包含内嵌图片。完整 ZIP 备份包含计划、任务、链接元数据与原始附件，承担迁移和恢复职责，不能以单份正文导出替代完整备份。

### 6.1 导入安全与资源限制

产品必须限制单文件、单批数量、压缩包展开大小、条目数量、解压比和处理耗时。本轮计划采用下列资源预算，由代码常量统一控制；最终值与通过情况以研究计划页面、README 和测试报告为准，正式版应按配置管理，不能宣称无大小限制。

| 资源 | 本轮计划上限 | 超限处理 |
| --- | --- | --- |
| 单个原始附件 | 50 MiB | 在读取前拒绝并解释原因，用户可在外部保留原件 |
| 尝试转为可编辑正文的文件 | 20 MiB | 在附件上限内仍可作为原件保存 |
| 单次提取文字 | 1,000,000 字符 | 停止转换并说明，不能假装完整导入 |
| 单份 PDF 文字提取 | 100 页 | 超出时保留原件，避免长时间阻塞 |
| DOCX／ODT 等 ZIP 容器展开 | 100 MiB，最多 2,048 条目 | 预检拒绝异常容器，不继续解压 |
| CSV 表格 | 1,000 行、50 列 | 超限保留原件，不继续转换表格 |
| 手动插入正文图片 | 单张 5 MiB | 更大图片使用普通附件模式 |
| 完整备份包 | 100 MiB | 同时考虑附件与清单的展开预算；失败时不覆盖现有内容 |
| 计划数量 | 2,000 份 | 达限时整理并保留备份 |

- 验证内容类型和实际文件特征，不只看扩展名；损坏的 DOCX／ODT 回退为附件并报告原因。
- ZIP 类格式只读取允许的文档部分，拒绝路径穿越与异常压缩包；XML 不加载外部实体或远程 DTD。
- HTML／粘贴内容使用标签、属性与样式白名单。剔除脚本、事件属性、危险 URL、嵌入页面、外链样式和自动网络加载内容。
- 外部链接只允许明确支持的协议；下载文件名进行规范化，不能由用户内容构造任意磁盘路径。
- PDF 解析和大型文档转换宜在 Worker 中执行，并可取消。无法及时转换时保留原件，不锁死编辑器。
- 备份恢复检查 schema、字段长度、数量、ID 冲突和附件大小；先校验再提交，失败时不覆盖已有数据。
- 第三方文档解析库要锁定版本、记录许可证，并通过本地已知样例验证。解析器失败不是用户内容丢失的理由。

## 7. 文献获取与来源追溯

### 7.1 获取策略

第一阶段优先接入明确的学术元数据与开放副本 API，而不是直接做无边界网页爬虫。Crossref 提供 DOI 及成员提交的学术元数据，可能包含摘要和许可信息；元数据记录不等于全文文件。[Crossref REST API](https://www.crossref.org/documentation/retrieve-metadata/rest-api/)。

OpenAlex 可以检索作品及相关实体，适合作为主题检索与引文线索来源。其数据对象与字段、认证和配额会变化，接入层应适配当前官方 API，并处理缺失字段、429、分页与重试。[OpenAlex API](https://help.openalex.org/api/) · [作品](https://help.openalex.org/data/works/) · [认证](https://help.openalex.org/api/authentication/)。

Semantic Scholar Academic Graph API 可作为论文、摘要和学术关系的补充来源；需要按实际授权、接口字段和限流开发。[官方 API 文档](https://api.semanticscholar.org/api-docs/)。

已知 DOI 时，可通过 Unpaywall 定位开放副本。它解决“哪里有可访问副本”，不负责通用全文编辑或保证每个 DOI 都有原文。[Unpaywall 官方说明](https://help.openalex.org/access/unpaywall/)。

| 来源适配器 | 首选职责 | 不能假定的能力 |
| --- | --- | --- |
| Crossref | DOI 匹配、书目信息补全、更新记录 | 所有条目都有摘要或可下载 PDF |
| OpenAlex | 主题／标题检索、作品关系、可用位置 | 一次请求返回全部记录，字段永远不变 |
| Semantic Scholar | 论文图谱元数据与摘要补充 | 所有论文都有全文，所有端点无条件无限量调用 |
| Unpaywall | 根据 DOI 定位开放版本与获取位置 | 开放获取标识等于任意再分发许可 |
| 本地目录／手动导入 | 用户已有的原始文件与个人资料 | 浏览器天然拥有整个磁盘的持续读写权限 |

具体下载必须区分免费访问与再使用许可，不绕过付费墙、机构认证或访问限制。用户拥有授权的本地文件可以导入。对无可用副本的条目显示出版方入口或“等待用户补充原文”。

### 7.2 入库去重

作品级优先按规范化 DOI、PMID、arXiv ID 等稳定标识匹配。没有稳定标识时，标题规范化、作者和年份相似度只能产生“疑似重复”，人工确认后合并。文件级用内容哈希识别同一份文件。

同一作品可以属于多个知识库，使用关联表记录库成员关系，不为每个库复制一份互不一致的摘要。预印本和正式稿保留版本关系；图谱可以按作品折叠，但引用仍指向实际使用的版本。

### 7.3 来源记录

每份元数据、摘要、文件和抽取结果都保留来源系统、原始 ID／URL、获取时间、许可字段、文件哈希、处理器版本和人工修订记录。多个来源冲突时，界面可查看来源，不用后来的空字段覆盖已有内容。

## 8. 摘要、关键词与主题图谱算法

### 8.1 摘要不是天然完整

“所有文献都有摘要”是希望达到的覆盖目标，不能作为数据事实。实际应区分：原作者摘要、元数据源摘要、从文件中抽取的摘要、用户补写摘要、模型生成概述，以及确实缺失摘要。

处理顺序建议：可信元数据中的作者摘要 → PDF 头部结构抽取 → 用户确认／补充。模型生成的概述单独存储并显著标记，不伪装为原论文摘要。缺摘要的文献仍可阅读，但不参与“摘要确切关键词命中”，除非用户主动切换到扩展匹配。

对于以倒排位置形式提供摘要的 API 返回，应按词位置恢复并保留原字段；不能把词表任意排序后当作原摘要。摘要文本需要处理 XML／HTML 标记、断行和 Unicode，同时保留原值供审计。

GROBID 可将科研 PDF 转为结构化 TEI，提供题名、作者、摘要、正文、参考文献及坐标等抽取能力。它适合作为后续后端解析候选，但抽取质量仍需在本项目的中英文和扫描件样本中验证。[GROBID 官方说明](https://grobid.readthedocs.io/en/latest/Introduction/)。

### 8.2 关键词方案分级

**最小可行方案不需要训练新算法。** 先用明确可解释的抽取和匹配建立基线，再衡量更复杂方法是否有收益。

| 级别 | 方法 | 优势 | 风险与控制 |
| --- | --- | --- | --- |
| A：规则基线 | 作者关键词、词典、短语匹配、停用词、TF-IDF／统计排序 | 易实现、可解释、可逐条核对 | 缩写、多词术语、跨语言同义关系处理有限 |
| B：语义辅助 | 词或短语向量、关键词模型、受控词表对齐 | 发现不同表达之间的联系 | 相似不等于同义；低置信结果需确认 |
| C：模型抽取 | 结构化输出关键词和原文证据片段 | 对领域短语和上下文较灵活 | 成本、幻觉与版本变化；无证据词不得作为确切命中 |

推荐先交付 A，允许人工合并别名；B／C 通过开关进入“推荐关键词”。任何自动归一化都保留规范词、原词、别名、证据位置和置信来源。

规范化包含大小写、Unicode、常见符号、词形与用户确认的缩写表。中文同义词与中英对应需要词表或人工确认；仅因向量接近就强行合并两个术语会污染整张图。

### 8.3 图谱关系的定义

基础图为二部图：`关键词 — 文献`。一篇文献可同时连接多个关键词；多个知识库只作为文献的范围与属性，不复制节点。

- `HAS_KEYWORD` 表示关键词确实来自摘要或作者关键词，并带来源、证据片段及版本。
- `SEMANTICALLY_RELATED` 表示语义近似的候选关系，必须用不同线型和说明。
- `CITES` 表示引用关系，只有取得相应来源时才展示。
- 手动计划链接使用单独关系类型，不能与上述关系混成“都有联系”。

用户选择关键词后，默认为“至少命中一个”的联合结果，另提供“全部命中”的交集。界面应明确当前匹配模式及摘要覆盖范围。

排序基线可考虑命中关键词数、抽取质量、时间、已读状态和用户置顶；这些维度分别展示或说明。引用量不直接代表质量，连线多也不等于值得优先阅读。

### 8.4 图谱美观与扩展

图谱的复杂性来自真实关系，清晰性来自交互控制，不通过随机添加节点制造“好看”。

- 默认只绘制选中关键词的一跳邻域；提供继续展开，而不是一次画完整库。
- 初始位置可持久化，增量加入少量节点，避免每次筛选全部重新飞散。
- 单关键词采用中心辐射，多关键词采用稳定的多中心力布局；碰撞约束避免标签重叠。
- 边透明、节点层次明确；只有选中或靠近时显示详细题名。使用缓动，遵循减少动态效果偏好。
- 超过显示预算时聚合为主题／年份／库群组，保留精确结果数与可检索列表；图谱不展示全部不等于数据消失。
- 首轮性能验收可取 200 个可见节点、600 条可见边作为交互测试场景，后续按设备实测调整，不将其宣称为最大数据库规模。
- 键盘可使用旁侧文献列表完成相同的选择与打开操作；颜色之外再用形状、标签或图例表达类型。

## 9. 科研智能体与个人知识库

### 9.1 “构建自己的知识库”的工程含义

本项目的第一条可行路线是文档解析、结构化存储、向量与全文索引、图关系和带证据生成，即 RAG。它在请求时检索用户资料，不意味着持续训练模型权重，也不等于模型完整理解所有文献。RAG 的原始研究将生成模型与可检索的外部记忆结合；它为工程路线提供依据，不替本项目证明正确率。[Lewis 等，RAG 原论文](https://arxiv.org/abs/2005.11401)。

后台“持续阅读”应实现为可取消、可恢复、只处理变更资料的任务队列。新增或修改文件才触发相应解析、摘要、关键词和向量更新；没有资料变化时，不反复调用模型重读整个库。

### 9.2 检索流程

1. 解析用户问题中的主题、时间、资料范围和输出目标；“近几年”必须转换为界面可见、可调整的具体年份。
2. 严格使用用户选定库和授权范围，先过滤后检索。
3. 结合全文关键词检索、向量相似检索和关键词图邻域，形成候选片段。
4. 对不同检索来源分别排序，用排名融合或校准策略合并；不能直接把全文分数与余弦分数相加。
5. 去重、重排、控制单篇文献占比，补充相反或不一致证据；记录召回来源。
6. 将足够上下文与证据 ID 交给模型，生成受约束的结构化答案。
7. 核对引用是否真的在检索结果中、是否支持相邻论断；证据不足时缩小结论或明确无法回答。
8. 返回答案、引用定位、资料覆盖、索引版本与不确定性。

Neo4j 提供全文与向量索引，可在图遍历前后组合使用。官方文档也区分检索源的评分语义；本项目选择排名融合而不是混加原始分数。[Neo4j 搜索索引](https://neo4j.com/docs/cypher-manual/current/indexes/semantic-indexes/) · [GraphRAG 使用指南](https://neo4j.com/docs/neo4j-graphrag-python/current/user_guide_rag.html)。

### 9.3 选题建议输出契约

每条候选方向至少包含：研究问题、库中已有证据、近期文献时间范围、可能未解决的缺口、相反证据、所需数据／设备、可执行的第一步、不确定性和需要补读的文献。

所谓“研究缺口”只能表述为“在当前检索范围内尚未发现……”或“这些证据提示……值得进一步验证”。资料库的空白不等于整个领域没有工作；系统不保证新颖性、可发表性或实验成功。

### 9.4 实验方案输出契约

建议文档包含假设、实验变量、对照／基线、数据划分、评价指标、消融设计、资源预算、复现信息、可能失败的原因和停止条件，并逐项标明参考哪篇文献。无法从文献得出的部分标为“待研究者决定”或“模型提出的建议”。用户确认后保存到研究计划，不自动执行实验或购买资源。

### 9.5 证据与可信度

模型语气自信不代表可信。产品要展示：是否读取全文或仅摘要、文献版本、解析质量、证据页码／段落、当前库覆盖的年份、是否有缺失全文与冲突结论。数值置信度只有经过标定才使用；早期以清晰的来源和局限说明代替虚构百分比。

## 10. 技术架构与存储职责

### 10.1 三个阶段不能混淆

| 阶段 | 主体实现 | 保存位置 | 能力边界 |
| --- | --- | --- | --- |
| 本轮浏览器试用 | 现有静态 HTML／CSS／JavaScript，加研究计划模块 | 当前站点来源下的 IndexedDB；主题等少量偏好可用 localStorage | 可试用计划与导入，不等于已有本地数据库服务或跨设备同步 |
| 本地正式版 | 桌面容器或本地 HTTP 服务＋前端 | 用户原文件目录＋SQLite＋本地索引与任务记录 | 可持续访问授权目录、处理大型文献、进行文件版本与备份管理 |
| 完整图谱与智能体 | 解析／检索服务、Neo4j、模型适配器 | Neo4j 图数据／向量索引；SQLite 主业务数据；原文件仍独立保存 | 需要真实接入、配置、权限、评测和运维 |

IndexedDB 能保存结构化数据及 Blob，并受同源策略与浏览器配额影响，适合本轮本地试用；清除站点数据、换浏览器或换端口会影响可见数据，因此必须提供备份导出。[MDN IndexedDB](https://developer.mozilla.org/en-US/docs/Web/API/IndexedDB_API)。SQLite 适合单设备应用的本地持久化，作为后续本地业务事实库；不将同一 SQLite 文件直接放到多人共享目录当成高并发云服务。[SQLite 使用场景](https://www.sqlite.org/whentouse.html)。

### 10.2 建议技术栈

| 层次 | 本轮 | 正式版建议及理由 |
| --- | --- | --- |
| 前端 | 延续现有 HTML／CSS／JavaScript，避免为局部试用重写已确认页面 | 随复杂度评估 TypeScript 和组件化；不以换框架本身作为目标 |
| 富文本 | Tiptap v3 编辑器、结构化文档与格式工具栏 | 延续文档模型，进一步完善长文、复杂导入和跨类型链接 |
| 图形 | 小规模 SVG／Canvas 原型 | Canvas／WebGL 图渲染与 Web Worker 布局；按真实可见节点预算优化 |
| 本地服务 | 本轮无需 | Python FastAPI 或同等 HTTP 服务，承担文件、任务、解析和检索边界 |
| 文献解析 | 本轮只针对计划导入 | PDF 解析＋GROBID 候选；扫描件采用独立 OCR；保存结构和页码 |
| 业务存储 | IndexedDB | SQLite 保存稳定对象、元数据、事务、任务与版本 |
| 原始文件 | 浏览器 Blob 附件 | 用户可迁移目录，内容哈希去重，原件与派生文件分开 |
| 图数据库 | 本轮是界面与本地关系演示 | Neo4j 为明确要求，存关键词／文献／链接等关系及可选向量索引 |
| 检索与生成 | 接口未连接时如实提示 | 全文＋向量＋图邻域融合，模型和 embedding 可替换 |
| 后台任务 | 导入进度与错误处理 | 可持久化任务队列；先用单机 worker，再按规模引入队列服务 |

“本轮”栏是本次实施范围，“正式版建议”栏是后续方案，不表示相关服务已经运行。Tiptap 的文档模型与扩展能力参考其[官方编辑器文档](https://tiptap.dev/docs/editor/getting-started/overview)；实际使用的扩展、版本、许可证及导入器应随源码保留记录。

### 10.3 存储一致性

SQLite 保存主业务事实，Neo4j 和向量索引作为可重建的查询投影。修改文献、摘要或关键词时，在业务事务中写入变更事件；worker 按版本幂等更新 Neo4j。界面显示投影同步状态，不采用跨两个数据库“写了一半也算成功”的做法。

删除或移出库时传播 tombstone；检索在索引更新前仍必须按有效文献 ID 与权限过滤。所有向量记录包含 embedding 模型、维度、分块版本和内容哈希，更换模型触发重建而不是混用不可比较的向量。

## 11. 主要数据模型

下表为完整产品的逻辑模型。浏览器试用只实现研究计划所需子集，字段可通过 schema 版本迁移；试用的待办嵌于富文本结构，独立任务表是后续扩展。

| 实体 | 主要字段 | 约束与用途 |
| --- | --- | --- |
| Workspace | id、name、settings、createdAt | 研究环境边界 |
| Vault | id、workspaceId、name、rootLocator、sourceType | 一个来源集合；不把本地绝对路径发给模型 |
| Paper | id、title、doi、authors、year、type、metadataVersion | 作品级 ID 稳定，规范 DOI 可唯一 |
| PaperVault | paperId、vaultId、folderPath、addedAt | 多库成员关系 |
| SourceFile | id、paperId、hash、mime、size、locator、version、license | 原件与作品区分，同一作品可多版本 |
| Abstract | id、paperId、text、kind、sourceId、version、quality | 作者摘要与生成概述分开 |
| Keyword | id、canonicalName、language、aliases、status | 词义规范化可撤销、可审计 |
| KeywordOccurrence | keywordId、abstractId、surface、start、end、method、score | 每条边能回到证据 |
| Chunk | id、paperId、sourceFileId、section、pageRange、text、hash | 结构化分块，不只按固定字符截断 |
| Embedding | chunkId、modelId、dimensions、vector、indexVersion | 严格区分模型与索引版本 |
| ReadingNote | id、paperId、content、citations、createdAt、updatedAt | 用户观点与摘录分开保存 |
| CitationAnchor | id、sourceFileId、version、page、quote、coordinates／offsets | 定位失效可以识别 |
| Plan | id、title、content、status、startDate、dueDate、tags、revision | 富文本为结构化内容或已清洗 HTML；不执行正文 |
| Task | id、planId、title、status、startDate、dueDate、order | 后续独立任务模型；本轮先使用正文待办 |
| Attachment | id、planId、name、mime、size、hash、blob／locator、importResult | 附件与转换正文分离 |
| InternalLink | sourceType、sourceId、targetType、targetId／unresolvedTitle、context | 出链为事实，反链由查询得到 |
| Conversation | id、workspaceId、title、scope、messages | 对话范围可复现 |
| Evidence | id、messageId、chunkId、sourceVersion、supportType | 引用绑定版本，不只有题名 |
| ProcessingJob | id、type、entityId、inputHash、stage、status、retry、error | 可恢复、幂等、可取消 |
| ChangeEvent | id、entityId、revision、operation、projectionStatus | 同步和重建索引 |

日期字段使用 `YYYY-MM-DD` 表示研究安排的日历日；`createdAt/updatedAt` 使用明确时区的时间戳。导出包含 `schemaVersion`、导出时间和附件目录／数据，不只导出屏幕上的文字。

### 11.1 Neo4j 图模型

建议标签包括 `Paper`、`Keyword`、`Vault`、`Plan`、`ReadingNote`、`Chunk`。每类节点拥有唯一业务 ID；不同类型同名不发生混淆。

| 关系 | 含义 | 关键属性 |
| --- | --- | --- |
| `(Paper)-[:IN_VAULT]->(Vault)` | 文献属于某库 | addedAt、folderPath |
| `(Paper)-[:HAS_KEYWORD]->(Keyword)` | 摘要或作者关键词支持 | abstractVersion、method、evidenceId |
| `(Paper)-[:CITES]->(Paper)` | 有来源的引用 | source、retrievedAt |
| `(Plan)-[:LINKS_TO]->(Plan)` | 用户明确建立的计划链接 | linkId、createdAt |
| `(ReadingNote)-[:ABOUT]->(Paper)` | 笔记归属 | sourceAnchorId |
| `(Paper)-[:HAS_CHUNK]->(Chunk)` | 结构化原文片段 | parserVersion |

查询应通过后端参数化 Cypher 执行，并先限定工作空间／库；不把数据库凭据或任意 Cypher 执行权限暴露给浏览器。模型可以请求已定义检索工具，不能自行拼接不受限制的数据库命令。

## 13. 实现流程

### 阶段 P0：本轮交付

- 重整为六项唯一主导航，保留登录注册页定稿。
- 为六个模块提供一致的页面设计及日夜状态；文献阅读明确呈现三列结构。
- 完成研究计划的浏览器本地试用：富文本编辑、计划管理、日期与正文待办、常见文档导入、任意格式附件、双向链接、计划图、备份导出／恢复。
- 其他新科研模块作为有明确标识的设计原型，真实服务未接入时不伪装成功。
- 提供源码、启动说明、测试说明和本项目文档。

### 阶段 P1：本地库与真实获取

实现本地 HTTP／桌面桥接、SQLite schema、目录授权、文件版本、元数据去重、Crossref／OpenAlex 等来源适配和下载队列。验证授权目录以外的文件不可读取，失败任务可恢复。

### 阶段 P2：原文阅读与笔记

接入正式 PDF 阅读器、文本层与定位锚点、GROBID／OCR 处理、原文摘录、随文笔记及可迁移导出。用扫描件、多栏 PDF、中英文混排和版本变更测试定位质量。

### 阶段 P3：摘要关键词与 Neo4j

建立可解释关键词基线、词表与人工校正、跨库去重图模型、幂等投影与局部图查询。先验证边有证据、去重正确和界面可用，再做大规模布局。

### 阶段 P4：科研智能体

接入结构化分块、全文／向量／图融合检索、重排、引用核对和模型适配。首先满足问答与方法比较，再开放选题建议与实验方案草案。

### 阶段 P5：评测与工程化

建立领域样本与标注、基线对比、误差分析、备份恢复演练、资源与隐私配置。只有评测显示收益，才引入更昂贵的关键词模型、复杂 GraphRAG 或微调。

## 14. 创新点与可验证贡献

本项目现阶段最可信的差异在于工作流和证据组织，而不是声称已经发明新的底层算法。

| 可实现的工程贡献 | 用户价值 | 如何验证 |
| --- | --- | --- |
| 阅读笔记、研究计划与原文引用连贯 | 灵感能够回到证据并转为下一步行动 | 完成“阅读→记录→关联计划→返回原文”任务，记录步骤与错误 |

| 区分计划链接图与主题证据图 | 用户能理解关系为什么存在 | 让用户解释两种图中边的含义，统计误解 |

## 15. 安全、隐私与可靠性

- 本轮计划内容默认保存在用户当前浏览器，不自动上传正文或附件给模型。后续云模型调用前展示会发送的范围。
- API 密钥保存在本地服务或桌面安全存储，不能写进前端源码、普通导出包或浏览器可公开读取的配置。
- 文献与网页文字是外部内容，可能包含恶意指令；检索系统将其视为数据，不能因此执行命令、越权读取文件或发送资料。
- 日志不默认记录全文、个人笔记、凭据或本地绝对路径；错误日志只保留排查所需信息。
- 浏览器保存有配额与被清理风险。保存失败要明确反馈，导出备份可在本地持有；下载成功与文件写入成功不能混为一谈。
- 文件权限、删除、迁移和备份恢复都要覆盖测试。正式版定期校验哈希，支持损坏文件隔离。
- 导入原件、清洗正文、派生文本、向量与生成内容分层存储；用户可以删除派生索引而保留原文。

### 16.2 完整产品验收目标

- 获取：API 超时、429、无摘要、无全文、许可证未知、重复作品与多版本都能正确处理。
- 阅读：选区引用定位准确；原件变化后能识别失效；不同文献笔记不串页。
- 图谱：每条确切关键词边可回到摘要证据；库范围与联合／交集筛选正确；大量数据有聚合而非假删除。
- 检索：采用带人工证据标注的题集，测 Recall@k、排序质量、引用准确与覆盖；按题型分析错误。
- 生成：区分正确事实、无依据论断、遗漏、矛盾与引用不支持；不能只看回答是否流畅。
- 可靠性：幂等处理、断点恢复、删除同步、索引重建与备份恢复实际跑通。
- 性能：记录设备、数据量、可见节点预算和延迟分布；不承诺脱离硬件的统一秒级指标。
- 隐私：没有授权时不读取库外文件、不上传私有正文、不记录密钥。

## 18. 本轮试用与启动方式

本轮使用的是浏览器本地试用，不需要先安装 Neo4j、Python 文献处理服务或模型服务。它主要让用户真实体验“研究计划”的编辑、导入、附件、待办与链接流程。其余研究模块的设计有助于确认信息架构，不应被误认成已连接检索、图数据库或自动科研系统。

源码交付包含已打包的 `dist/`。安装 Node.js 22 或以上版本后，在项目根目录运行：

```bash
npm start
```

打开终端显示的工作空间地址，默认是 `http://127.0.0.1:8000/home.html`；研究计划可直接访问 `http://127.0.0.1:8000/plans.html`。仅体验打包版本不需要先重新构建。

也可以在已安装 Python 的环境中启动静态服务：

```bash
python -m http.server 8000 --directory dist
```

选择“研究计划”即可试用。登录注册入口为 `http://127.0.0.1:8000/index.html`；真实账号服务尚未接入时，直接访问工作空间用于本地功能体验。日夜设计画廊入口为 `http://127.0.0.1:8000/designs.html`。

建议固定使用相同浏览器、域名和端口。`127.0.0.1:8000`、`localhost:8000`、不同端口和在线站点分别拥有不同的浏览器数据范围。关闭页面不会主动清除已保存计划，但清理站点数据、隐私模式或浏览器存储策略可能导致数据不可用，重要内容请先导出备份。

不建议直接双击 HTML 文件启动完整试用，因为 `file://` 下的模块、文件读取、浏览器数据库与解析器行为可能受限。只有修改源文件需要安装依赖并重新构建；具体命令、当前限制、导入说明与测试结果见项目 README 及 [QUICKSTART.md](QUICKSTART.md)。

## 19. 已明确的产品决策

1. 保留已经定稿的动态登录注册页，不将本轮工作扩展为重新设计认证页面。
2. 一级研究导航为六项，研究计划吸收任务、文档和计划关系图；知识库管理不重复充当阅读库。
3. 文献阅读桌面采用三列，左侧宽导航变成目录；移动端用分区切换。
4. 跨库主题图谱以摘要关键词与文献关系为基础，Neo4j 是后续明确使用的图后端。
5. 先实现可解释规则与人工校正，再评估复杂抽取算法；先做 RAG，再判断是否有必要微调。
6. 所有文件的“可传入”通过原附件保存达成；可编辑转换按格式能力诚实说明。
7. 本轮优先使研究计划可实际试用，其他新科研服务明确处于设计／待接入阶段。
8. 真正的贡献必须通过用户任务与检索／生成评测证明，不以漂亮图谱或流畅回答代替科研有效性。
